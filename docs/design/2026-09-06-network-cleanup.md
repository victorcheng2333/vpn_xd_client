# 断网后的网络清理

## 本轮依据

故障日志由用户提供的 Claude 排查记录给出：utun 已销毁，但 configd 的 IPv4/DNS 服务键仍以旧 utun 为主接口。代码核对确认，原助手在 8 秒后使用 Foundation Process.terminate，vpnc-script 的 DNS 删除位于可能阻塞的路由操作之后，助手自身没有清理兜底。

本机独立信号实验确认：Process.terminate 会把 TERM 送到孙进程；向 OpenConnect PID 直接发送 TERM 不会如此。上游 [MR !425](https://gitlab.com/openconnect/openconnect/-/merge_requests/425) 同样以脚本进程组隔离解决信号中断配置清理的问题；[9.21 的 script.c](https://gitlab.com/openconnect/openconnect/-/raw/v9.21/script.c) 已包含 setpgid。本机已从 9.12 升级到 9.21。升级本身不替代本客户端的异常退出清理。

## 实现（1.1.7／助手 4）

1. 物理网卡就绪判断保留。已建立会话离线时暂停主动恢复，不主动断开；网络就绪后再进行有期限的旧会话恢复。手动断开、退出和未完成登录的取消仍然生效。
2. 普通停止只使用正数 PID 发送 SIGINT、SIGTERM。40 秒仍不响应时才对该 PID 发送 SIGKILL；不会用 Foundation 的进程组终止方法。
3. 特权助手将 OpenConnect 的脚本固定为自身的内部入口。此入口只允许 root 和 root 私有会话目录，普通用户的 sudoers 没有该入口权限。不会从服务器日志推断 utun 所有权。
4. connect 钩子执行前记录 PID、utun 名称、分配地址和 DNS，写入会话标记。已有不明服务键时拒绝覆盖。记录不包含密码、cookie 或认证响应。
5. vpnc-script 使用 posix_spawn 的 SETPGROUP 创建独立进程组，标准输入为空，不继承助手的其他描述符。脚本有 15 秒执行预算；超时才终止这个明确归属的脚本组，防止清理之后仍有脚本继续写入。该预算是本客户端策略，不是 OpenConnect 协议要求。
6. disconnect 脚本执行前先清除本次 IPv4/DNS 状态，避免脚本的路由命令继续使用死隧道 DNS，但保留 XDVPN 归属标记。脚本完成／失败后再次清理并复核；OpenConnect 进程退出且脚本输出关闭后，父助手再次核对。通过 SCDynamicStoreSetMultiple 删除本次 IPv4/DNS 键和归属标记，再读取确认结果。清理步骤不需要默认网关或 DNS，configd 可以重新选择物理服务。
7. 若归属标记不匹配、关键地址／DNS 被更改、退出后等待最多 2 秒，同名接口仍在使用，或配置删除未成功，则报告包含 PID、utun、具体键和记录目录的清理错误，阻止在残留未清理时登录。接口等待期间每次重读归属、地址和 DNS，不能拿等待前的快照直接删除。再次连接会先重试同一记录的清理。不会把“进程退出”描述为“网络清理成功”。

8. 恢复钩子超时与初次配置失败分开：attempt-reconnect／reconnect 的 watchdog 超时返回 0 并输出固定的提示，避免 OpenConnect 的通用 Script error 被助手误判为致命配置失败。其他非零脚本结果仍报错。disconnect 超时后只要原生清理复核通过，也返回 0；用户主动停止期间通用脚本错误交给最终清理判断，真正的清理错误仍是致命错误。
9. 助手和每个脚本包装器持有清理记录的共享文件锁；启动扫描只获取可独占的记录，随后确认记录的 PID 已不存在、utun 已销毁、归属和地址匹配，才清理遗留状态。不会结束旧 PID 或删除其他客户端状态。旧版无锁记录需先等待至少 60 秒，避免与尚未退出的旧包装器并发。无法确认清理时停止此次新连接，保留记录供下一次重试。
10. 物理网络恢复后的 3 秒会话恢复期限保持原策略，Auto Connect 关闭时超时会清理并保持断开，以减少死隧道占用普通网络的时间。物理就绪不代表互联网可达；需要网页登录或不能访问 VPN 的 Wi-Fi 仍需实测。本轮不恢复 OpenConnect 完整 300 秒等待窗口。

## 范围与限制

- 只处理有本次记录和归属标记的 utun IPv4/DNS 服务键。不会全局扫描删除其他 VPN 的键，也不会自动删除旧助手、sudoers 或 Hillstone 服务。
- 仍依赖 vpnc-script 执行通常的路由、接口与 resolv.conf 配置。异常时的原生兜底针对本次故障的动态服务键，不是完整的任意系统配置快照恢复；持久 networksetup DNS、自定义 hooks、路由备份文件需要另行处理。
- 私有记录在成功后删除，清理失败时保留以供排查。新助手在连接前扫描本客户端遗留记录，但没有常驻守护进程。若权限助手本身被 SIGKILL，不能保证立即清理；若其 OpenConnect 仍活着或有脚本持锁，下一次启动也不会杀它或强行删除状态，需要先让原会话退出。
- 归属校验是有意保守的。记录不足或同名接口被复用时宁可报错，也不删除不能确定属于本次会话的配置。
- 本轮未实现 Network Extension。其他产品的架构差异不能直接证明当前实现的系统行为。[Tailscale 的 DNS 管理代码](https://raw.githubusercontent.com/tailscale/tailscale/main/net/dns/manager_darwin.go) 提供了识别自身配置的参考；本实现不照搬其全局服务标识和启动清理流程。

## 验证含义

信号实验使用真实父子孙进程。vpnc-script 回归运行本机安装脚本的实际控制流，但路径和网络命令均使用隔离替身，复现 route 阻塞早于 scutil 清理；配置归属／删除复核通过可注入存储测试。实际 SystemConfiguration 做了只读检查。尚需管理员升级版本 4 助手后，用真实公司 VPN 验收关闭 Wi-Fi 30–60 秒、恢复网络、手动离线断开以及百度和公司域名的可达性。

本轮增加包装器阶段处理、接口延迟销毁／等待中归属改变、共享锁保护、遗留记录扫描与失败后重试测试。原测试只把 watchdog 和手动原生清理串起来，未覆盖 wrapper 返回值经过 OpenConnect 日志分类的组合；现在明确断言恢复钩子返回 0、输出只映射为提示，而初次配置失败与原生清理失败仍返回错误。

# 质量监控：日志、面板与告警

## 当前落地范围

1.1.9 在现有原生 macOS 客户端中增加「连接质量」页。继续采用本机受限滚动日志，不引入远程服务，也不改变 VPNCore、版本 4 助手的通信协议、网络探测、认证和清理策略。

日志有三层用途：已有的过程诊断、可聚合的质量事件、本地告警状态变化。质量事件在业务状态入口产生，不从中文日志中事后推断成功率；助手当前仅提供归一化消息，认证、证书、网络配置失败只对固定已知文本作兼容映射，其他失败使用未知助手错误分类。

## 事件和统计口径

每行保留原有时间、App 会话、应用版本、来源、处理前状态和 Auto Connect 开关。schemaVersion 2 增加 build、osVersion 和可选 quality：

| 字段 | 含义 |
| --- | --- |
| id | 单条质量事件 UUID，供后续上报去重 |
| timestamp | 事件时间，Unix 秒；外层 timestamp 仍为 UTC 毫秒精度文本 |
| connection | 本次连接尝试 ID；取消任务不改变后续清理日志的连接 ID |
| kind | attemptStarted / Succeeded / Failed / Cancelled，recoveryStarted / Succeeded / Failed / Cancelled，observationEnded，uncleanExit |
| reason | 用户、退出、切网、物理离线、睡眠、传输中断、恢复超时、助手失联、准备失败、认证、证书、网络配置、未知助手失败等封闭枚举 |
| durationMS | 结果事件的单调时钟耗时，毫秒；包含该轮期间离线和睡眠等待 |

表中缩写的事件类型均带前缀，例如 attemptSucceeded、recoveryFailed。生命周期事件的 connection 可以为空；上次会话 ID 另见 app.previous_exit_unclean 日志。

- 一次新尝试最多产生一个成功、失败或取消结果；助手重复发送 connected 不重复计数。成功率只用已观测到的完成结果：成功 /（成功 + 失败）。取消、进行中和崩溃前丢失结果的尝试不进入分母。
- 连接耗时从开始准备助手到助手确认隧道已建立。P95 用成功样本的 nearest-rank 计算，显示样本量；样本少时只能作为排障参考。
- 一个已建立隧道每轮恢复只记一个开始和一个结果。离线期间重复 connected 不结束恢复；恢复成功也不增加新登录次数。恢复超时、助手错误和意外停止结束本轮计时。
- observationEnded 表示本次质量观测结束，包括用户请求断开；不代表进程或系统网络清理已经完成。实际清理仍以原有助手 stopped 与清理诊断为准。
- 面板取最近 24 小时的保留事件，日志仍为 4 × 1 MiB；因此不承诺完整 24 小时，更不把此窗口称为团队 SLA。内存最多 10,000 条质量事件。
- 重启异步加载轮转文件，加载先于本次 app.started 的写入。旧版记录兼容读取，但不生成虚假的历史质量样本。损坏行跳过并提示，特殊文件、链接、异常大小文件拒绝读取。日志失败不影响 VPN。

## 本地告警

| 规则 | 默认触发条件 | 解除 |
| --- | --- | --- |
| 连续失败 | 10 分钟内最后 3 次完成尝试均失败 | 成功打断或窗口内样本不足 3 次 |
| 成功率下降 | 10 分钟内至少 5 次完成尝试，成功率 < 80% | 成功率恢复或样本不足 |
| 频繁中断 | 10 分钟内引擎报告的中断或意外结束至少 3 次 | 窗口内不足 3 次 |
| 异常退出线索 | 24 小时内启动时发现上次会话缺少正常退出记录 | 检测事件移出窗口 |

业务事件立即评估，运行期间每 30 秒再评估。每条规则仅在触发和解除时写 alert.triggered.<rule> / alert.resolved.<rule>，持续异常不刷屏。频繁中断排除主动切网、物理离线、睡眠恢复；同一恢复失败后进程结束不算第二次。以上阈值是本机排障初始值，集中上线前应根据实际基线调整。

告警只显示在客户端并落本地日志，没有系统推送、邮件或即时消息通知。文件不可写和历史不完整在面板单独提示。

## 崩溃与业务质量边界

缺少 app.quitting 只能证明没有观测到退出记录，可能来自崩溃、强制退出、断电或尾部日志未持久化。当前不是 crash-free sessions 指标，不采集堆栈，也不声称能分析具体崩溃根因。损坏历史时不推断异常退出；日志已删除、助手在 App 退出后崩溃、App 从未成功写出记录等情况无法覆盖。

现有 OpenConnect 状态只说明隧道建立或恢复。不能据此推断 DNS、业务 HTTP、延迟、丢包、吞吐或 TCP/DTLS 通道质量。业务探测需要指定稳定、无副作用的公司健康检查目标，并规定成功条件、超时、频率以及离线/睡眠暂停规则；探测结果使用独立事件，不修改连接状态或触发重连。

## 集中监控的下一阶段

建议沿用质量事件作为数据来源，按「客户端持久队列 → 已有日志/监控接入服务 → 集中聚合 → Dashboard → 服务端告警」接入。先确定团队已有平台、保留期限和告警接收方，再选协议与部署方式，避免把终端直接变成告警发送服务。

集中接入需补充：经授权的随机安装标识（不用账号、硬件序列号）、可靠上传队列、批量与失败退避、事件 UUID 去重、流量和磁盘预算、采集缺口/上报延迟指标。当前滚动诊断文件会被覆盖，不能直接充当可靠上报队列；未上报设备不能算健康。

团队面板至少按应用版本、构建号、系统版本聚合成功率与耗时分布、失败原因、恢复耗时和中断情况；避免用连接 UUID 作高基数指标标签。跨日可用率还需要明确“用户期望连接”的时间分母及离线/睡眠的排除口径。崩溃分析需独立的系统崩溃报告或采集组件、版本匹配的符号文件、堆栈聚类和脱敏；异常退出提示不能替代这些数据。

集中告警由服务端处理最小样本量、持续窗口、按版本/设备组去重、通知冷却、恢复通知和运维静默。最终阈值和接收人尚未确定，因此本轮没有远程上传、创建外部 Dashboard 或发送通知。
